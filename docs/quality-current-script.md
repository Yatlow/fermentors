# בקרת איכות — שימוש בפרויקט Apps Script הקיים

## התכנון שנבחר

לא מקימים Apps Script חדש ולא משתמשים ב־brewcrew בתור בעלים.
נשתמש **בפרויקט Apps Script הקיים של הפרמנטורים**, המקושר
ל־`server/.clasp.json`. המשתמש שמבצע את פריסת ה־Web App הקיים הוא זה
שמעניק הרשאות ל־Sheets, Drive ולשליחת מייל.

**אין שינוי DNS ואין התחברות של המדווחים.**

### זרימת התהליך

1. הציבור ממלא טופס ב־Firebase Hosting.
2. Cloud Function בודקת Turnstile, ולידציות, קבצים, הגבלת כמות דיווחים ושומרת
   אסמכתה ומדיה באופן פרטי ב־Firestore וב־Cloud Storage.
3. Cloud Function שולחת **מיד** לכתובת Apps Script הנוכחית פעולה חדשה וייעודית
   `QualitySignedDispatch` הכוללת רק מזהה דיווח, חותמת זמן וחתימת HMAC.
4. `server/post.js` מנתב **רק את הפעולה הזו** לפונקציה
   `qualityHandleSignedDispatch_` בקובץ החדש `server/QUALITY_REPORT_SERVICE.js`.
   הפונקציה מאמתת חתימה סודית, חותמת זמן וזהות דיווח לפני כל גישה לנתונים.
5. Apps Script הקיים מעבד מיד: מוסיף שורה בגיליון, מעביר קבצים ל־Drive ושולח
   **מייל אחד ליוחאי על כל דיווח**. החל מהאירוע השלישי הנפרד של אותו סגנון
   ואותה אצווה, המייל עצמו מציג אזהרה.
6. כשהפעולה הצליחה הטופס מציג מספר פנייה אמיתי; אם כשלה, הדיווח נשאר
   ב־Firestore ומוצגת אסמכתה זמנית. שחזור באמצעות `qualityRecoverQueued`
   הוא פעולה יזומה, **לא סריקה אחת לחמש דקות**.

## הגנה על הפרמנטורים הקיימים

- **כל הפעולות הישנות** של `doPost` ממשיכות לעבור
  `authenticateFirebaseRequest_`, לרבות בדיקת `approvedUsers`. ההחרגה
  היחידה היא `QualitySignedDispatch` שדורשת HMAC חזק מתוך Cloud Function.
- לא שינינו את קוד הבישולים, קריאת המדידות, המיפויים או הטריגרים.
- תוספת אחת ל־`server/appsscript.json`: הרשאת
  `https://www.googleapis.com/auth/script.send_mail`. ההרשאות האחרות
  אינן משתנות. לכן יש לבצע אישור הרשאות מחודש בחשבון שמפרסם את הסקריפט.
- יש לבדוק את ה־`doPost` הרגיל ואת הקריאה החתומה בבדיקות קצה לפני עדכון
  ה־deployment הקיים. Web App קיים מריץ גרסת קוד שפורסמה, ולא בהכרח את
  הקוד העדכני בעורך.

## פעולות חד־פעמיות לפני פריסה

1. לברר מי החשבון **שמפרסם את ה־Web App הקיים**. לוודא שהוא מורשה לערוך את
   גיליון בקרת האיכות `19urjK3mUk1vO1clZ2IFDq-3ORqLeX5edBLmBeDwIud4`
   ולהוסיף קבצים לתיקיית המדיה
   `1FrGg-gBKRyCSsw4EHTq8qb6zJEpWaQSn`. המייל יישלח דרך MailApp
   מאותו חשבון, לא מ־brewcrew אלא אם הוא החשבון שמפרסם בפועל.
2. לאשר, בהתאם למדיניות אבטחת הארגון, הרשאת
   `roles/datastore.user` לקריאת תור Firestore והרשאת
   `roles/storage.objectViewer` בבאקט המדיה הפרטי עבור **החשבון הזה**.
   אם העובד אמור למחוק את המדיה הזמנית, נדרשת גם הרשאת מחיקה באותו באקט.
3. ליצור מפתח אקראי באורך 48 תווים לפחות, ולהגדירו בשם
   `QUALITY_WEBHOOK_SECRET` בתוך **Script Properties של הפרויקט הקיים**
   וב־Secret Manager של Firebase. לא לשתף את ערך המפתח בצ׳אט, ב־GitHub
   או בלוגים. חשבון ההרצה של Cloud Functions חייב להיות מורשה לקרוא אותו.
4. להעלות את הקבצים המעודכנים אל פרויקט Apps Script **הקיים**, לא אל פרויקט
   נפרד. לוודא שלא נמחקים קבצי שרת קיימים. להריץ ידנית
   `qualityVerifyCurrentProject` לפני פרסום גרסת Web App חדשה.
5. לעדכן את גרסת ה־Web App הקיים ולבדוק שהנתיב הישן עובד כרגיל באמצעות
   משתמש מאושר, ושקריאה ללא Firebase ID Token לפעולה רגילה עדיין נדחית.
6. להגדיר GitHub Environment `production` → Variables →
   `QUALITY_APPS_SCRIPT_URL` אל כתובת ה־Web App הקיימת, אותה כתובת שכבר
   משמשת את הפרמנטורים ב־`src/config/runtimeConfig.ts`.
7. לפרוס ידנית את Cloud Functions של איכות **אחרי** פריסת ה־Apps Script.
   יש לנקות אז את פונקציות ה־OAuth הישנות ואת משימות Cloud Scheduler
   `qualityReportWeekly` ו־`qualityReportMailRetry` אם עוד קיימות.
8. לבדוק דיווח אחד שמסומן כבדיקה בגיליון האמיתי — תוכן, מדיה, דוא״ל,
   אסמכתה, ספירת אצוות, מניעת כפילויות — ורק אז למזג את PR #252.

## אבטחה וגבולות

- טופס האינטרנט לא מקבל ולא מחזיק את סוד החתימה.
- הקישור הקיים של Apps Script כבר מופעל כ־Web App עם גישה ציבורית, אך
  כל שאר הפעולות דורשות Firebase Authentication. אין לפתוח פעולה נוספת
  בלי בדיקת חתימה או הרשאת משתמש.
- לא נוצרת בקשת OAuth חיצונית ב־Google Auth Platform; הסקריפט משתמש
  באסימון Google המנוהל עבור חשבון הפריסה הקיים.
- פעולה שהצליחה מדווחת מספר פנייה רק אחרי כתיבה בגיליון וקריאת MailApp.
  אירוע שנכשל נשמר בתור לשחזור ידני.
- במקרה נדיר שבו מייל נשלח אך אישור העיבוד נכשל, ניסיון חוזר עשוי לשלוח
  הודעה כפולה; יש לנטר ולהקשיח לפני שימוש בנפחים גדולים.
